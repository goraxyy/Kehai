# Engineering decisions

The decisions that shaped how Kehai is built: what was chosen, what it was chosen over, what
it costs, and the numbers behind it. The newest work, the scaling of the shop and the endless
maze, is covered in the most detail, because it changed the most. The plans themselves live in
[`IDEAS.md`](../design/IDEAS.md) (under *Scaling* and *Infinite maze*); this file is the
record of why.

Each decision says where it lives in the code and which pull request made it.

## 1. How the project is kept

### 1.1 The repository holds code and documents only

**Decided.** Git gets scripts (with their `.meta` files, so GUIDs survive) and Markdown. Art,
scenes, prefabs, materials and project settings stay on the Mac (#5 onward).

**Why.** Models, textures and scenes are large binary or generated files, some of the art isn't
ours to publish, and a 92 MB scene (§4.1) doesn't review.

**What it forces.** Anything the game needs that isn't art is made from code:

- Aiko installs herself into the store when it loads (`AikoBootstrap`).
- Speech bubbles, the eyelids, the menus and the HUD are built in code.
- Some materials are made in code: the shoppers' colour and Aiko's props.
- The product prefabs are generated by the importer.
- Authored data is C#: the catalogue, the planogram and the store layout.

**What it costs.**

- Scene wiring can't be reviewed.
- A value saved in a prefab can drift from the code's default. The shoppers' speech bubble
  sat inside their bodies because `Teto.prefab` kept a 0.4 m offset written for an older model
  with its pivot at the feet.
- Settings that matter are guarded by tests instead: `PerformanceSettingsTests` fails if the GPU
  Resident Drawer is switched off.

### 1.2 Verifying without disturbing the open editor

**Decided.**

- **Compile checks:** offline, with the editor's own compiler response files.
- **Batch runs** (tests, bot shifts, builds): on an APFS clone of the project, only while the
  editor is closed.
- **While the editor is open:** checks run inside it, through its bridge.
- **Branch work** happens in git worktrees, never by switching branches in the main checkout.

**Why.** The Mac has 8 GB of memory, and two Unity processes don't fit. The main checkout is
the one the user's editor has open.

**Also.** Nothing a check runs makes sound. Batch runs are silent through
`SoundSettings.Audible`, and in-editor runs mute the editor and restore it afterwards.

## 2. Measuring

### 2.1 One fixed way to measure render cost

**Decided.** Render cost is the camera's render time in Play at 1080p, best of three, over four
fixed views of the store:

- down a long run;
- the drinks aisle;
- produce from the door;
- along the back wall.

Every change to rendering is measured this way, before and after.

**Two rules learned the hard way.**

- **Let frames pass between changing something and timing it.** The GPU Resident Drawer
  registers objects a frame later. #39 timed in the same frame and reported 4.2 ms for stock
  the drawer hadn't even taken up; the real figure was 19.6 ms (#40).
- **Take a picture with every measurement.** It proves the thing being timed was drawn.
  Leftover hidden objects from an earlier experiment once made the stock look 16 ms dearer
  than it was.

## 3. Rendering

### 3.1 The GPU Resident Drawer, with GPU occlusion culling (#34)

**Decided.** URP's GPU Resident Drawer draws ordinary `MeshRenderer`s through
BatchRendererGroup instancing, culls on the GPU, and with occlusion culling on skips what the
shelves hide.

| | mean of the four views |
|---|---|
| off | 18.9 ms |
| on | 5.1 ms |
| on, with GPU occlusion culling | **4.5 ms** |

**Instead of** hand-built instancing or static batching, which can't occlusion-cull per object.

**What it needs.** *BatchRendererGroup Variants* set to **Keep All** in the graphics settings.
Without it the editor quietly leaves the drawer off, and builds lack its shaders. These are local
settings, so a test guards them (§1.1).

### 3.2 Each room lit by its own lights (#30, #31)

**Problem.** The ceiling spots cast no shadows (240 shadowed lights would cost too much), so
they lit the next room through the walls, and the sun lit the staff room.

**Decided.** `RoomLighting` puts each room on its own rendering layer:

- a light only reaches its room's layer;
- a still object carries the rooms it stands in (a wall carries both sides);
- anything that moves keeps the default layer, which every light reaches.

**Gotcha.** URP silently drops rendering-layer bits that have no name in *Tags and Layers*. The
rooms were first on layers 8–12, so every room went dark. They're on 1–5, which URP names by
default, and the code warns rather than splitting the rooms if those names are missing.

### 3.3 Materials made by name must be in the build (#22)

Materials made in code with `Shader.Find` (`URP/Unlit`, `URP/Particles/Unlit`) were stripped
from builds, because no material asset used them. The build script adds them to *Always Included
Shaders*. Code-made materials use the URP Lit shader where they can, which the products already
keep in the build.

### 3.4 Products shown at 1.5× real size (#30)

**Decided.** Labels have to read from the aisle, so products are 1.5× real size, capped at
0.5 m tall. Meshes aren't imported readable, since nothing reads them on the CPU.

**Superseded.** The earlier product "blocks" (one mesh per product, up to 6 × 3) came to about
10 million vertices and doubled an aisle's cost (14.4 against 8.1 ms). #29 capped and LOD'd
them, and #30 replaced them with one item per slot.

## 4. The shelves: from 33,000 objects to data

### 4.1 Shelves as data (#35, #36)

**Before.** The shelf grid (#30) cut every board into 0.5 m squares and filled each with real
slots: 16,502 slots on 189 bays.

- Every slot was a GameObject with a trigger collider and a script.
- Every item standing on it was another GameObject, with a renderer, a rigidbody, colliders and
  scripts, baked into the scene as a prefab instance.

That's about 33,000 GameObjects for the stock alone. Shoppers looking for a product scanned
every slot, and the replay recorder read every slot on every tick.

**Why the scene was 92 MB, and why it's 6.2 MB now.** A Unity scene is a text file:

- every GameObject and every component is a block of YAML;
- a prefab instance also lists, one entry each, every value it overrides (position, rotation,
  parent, product).

33,000 such objects come to about 2.8 KB each on average, which is where the 92 MB went (it also
took 16 s to save).

After step 2, none of that is saved:

- the slots are rebuilt at load from the planogram, which is code;
- the items you see are hidden objects marked never to be saved (§4.2);
- the migration (*Kehai/Store/Migrate to Data Shelves*) also deleted the old six-to-a-board
  slot objects that every shelf prefab still carried from before the grid.

That last step is why the scene ended up smaller than before the grid existed (19.5 MB). What's
left is the building itself: 4,662 GameObjects, 6.2 MB.

**Decided.** A slot is a plain C# record (`ShelfSlot`): where it is on its bay, which way it
faces, what the planogram wants there, and what stands on it. `ShelfStock` holds them all,
filed three ways:

- **by place,** on a 2 m grid, for "what's within reach of here";
- **by bay,** so a bay Aiko moves between shifts takes its slots with it;
- **by change,** which feeds the drawer and the replay recorder.

**What changed with it.**

- **Lookups** go through the grid and per-product lists instead of scanning 16,502 slots.
- **Replays** record only the slots that changed.
- **Items exist only off the shelf.** An item becomes a GameObject when the player or a shopper
  takes it, or Aiko knocks it off, made at the slot's exact pose. Put back, it's destroyed and
  the slot records what's on it.
  - **No pool.** Items leave shelves a few times a minute, not hundreds of times a second, so
    one wasn't worth its complexity.

### 4.2 How the stock is drawn: three tries (#35, #38, #39, #40)

Slots have to look stocked, without being GameObjects in the scene. Three ways were built and
measured:

| how the stock was drawn | what the stock added, over the four views |
|---|---|
| `Graphics.RenderMeshInstanced` per 10 m cell, product and room (#35) | 7.3 ms |
| the same, merged into one call per product per view (#38) | 4.2–4.9 ms |
| one bare render object per slot, drawn by the GPU Resident Drawer (#39, #40) | **2.2–2.4 ms** |

**Why instanced calls lost.** They can't skip what the shelves hide: every item in the frustum
is drawn, even behind two rows of shelving. The GPU Resident Drawer culls each object, hidden
ones included.

**Decided.** `ShelfDrawer` keeps one template per product and room. The template is the
product's mesh and materials, the room's light layer, and no collider or script. Each stocked
slot gets a copy:

- the copies are hidden and never saved, so the scene stays small;
- a slot that empties or fills swaps its copy through a pool;
- a full rebuild reuses the copies it has, so the editor can show the stocked shop live, with
  nothing baked.

**`Instantiate`, not `InstantiateAsync`.** Copies made by `InstantiateAsync` are never taken up
by the GPU Resident Drawer. They're drawn the ordinary way, at 19.6 ms. Both take about 0.6 s
for all 16,500.

| copies made with | mean of four views |
|---|---|
| no stock | 2.4 ms |
| `InstantiateAsync` | 19.6 ms |
| `Instantiate` | **4.8 ms** |
| the real product prefabs | 5.2 ms |

### 4.3 Aiming without colliders (#35)

**Decided.** `ShelfAim` casts the player's ray to the first solid thing in reach: a board, a
bay's back, a wall. It then tests the ray against the boxes of the slots near it that stand in
front of that. The player's interact code takes whichever is nearer: something with a
collider, or a slot.

**Instead of** 16,502 trigger colliders, which physics has to keep in its broadphase.

**Checked.** On 400 rays, `ShelfAim` agreed with a brute-force test of every slot every time.

## 5. The endless maze

Built in #37, in a scene of its own (*Kehai → Endless → Open an Endless Maze*).

### 5.1 Seeded, chunked and deterministic

**Decided.** The world is a grid of 25 m chunks, each 5 × 5 cells of 5 m. A chunk is worked out
from `hash(seed, chunk_x, chunk_z)` alone, so the maze is:

- **endless:** nothing is stored, and a chunk is made when it's needed;
- **stable:** walk away and back, and the same aisles are there;
- **reproducible:** a seed is a whole world, which the evaluation needs. Procedural layouts stop
  an agent memorising one map.

The hash is a small integer mix, and the random numbers are xorshift32. They're the same on
every machine and need no stored state.

### 5.2 The generator: matched borders, a spanning tree, then braiding (`MazeGenerator`)

1. **Borders first.** Each border between two chunks takes its five edges from the border's own
   hash, with at least two open. Both chunks compute the same border, so aisles always meet,
   with no need for the neighbour to exist.
2. **A spanning tree inside.** Every inside wall starts closed. Kruskal's algorithm, in a
   shuffled order, opens just enough walls to join every cell. With the guaranteed openings in
   the borders, the whole world is one connected place.
3. **Braiding.** 75% of dead ends get one more opening, and another 12% of walls open for
   loops.

**Why braid.** A perfect maze is about a third dead ends: miserable to shop in, and a chase with
no way round is frustrating rather than tense. Aiko's herding needs loops.

**Alternatives considered** ([`IDEAS.md`](../design/IDEAS.md)):

| option | why not |
|---|---|
| Wave Function Collapse | prettier, but can hit contradictions, and seams between chunks need care |
| a perfect maze (DFS/Kruskal alone) | all dead ends |
| BSP rooms and corridors | reads as a dungeon, not a shop |

**Tested** (`EndlessMazeTests`, over 64 chunks and four seeds):

- every cell reachable from every other;
- under 8% dead ends (2.6–3.7% measured);
- neighbours agree on their border;
- nothing built twice;
- the same seed gives the same chunk.

### 5.3 What stands where

- **Walls.** A closed wall is a two-sided 4 m shelf bay, the store's own prefab.
- **Corners.** Where walls meet, a 1 m pillar.
- **Ownership.** Each chunk builds its own walls, its east and north borders included, and the
  corners it owns, so nothing is built twice.
- **Pivots.** Prefabs aren't centred on their pivots, so each piece is placed by the middle of
  its footprint.

**Checked in Play.** All 434 runs stood on the middle of a standing wall, and all 557 pillars on
a corner where walls meet.

### 5.4 Streaming (`EndlessMaze`)

**Building.**

- Chunks within 2 of the player's are built (a 125 m square, 25 chunks), nearest first, one a
  frame.
- A chunk comes down only when it's more than 3 away, so walking back and forth over a border
  doesn't build and tear down the same chunks.

**Each chunk gets:**

- shelf runs and pillars, from pools;
- a shell (floor and its collider, ceiling, 25 ceiling lights with lamps), pooled and moved
  from chunk to chunk;
- its stock, as data: one section per chunk, stocked by the same planogram code as the store.

**State of chunks you leave.** Only differences from the plan are kept: which slots are empty, or
hold something else. A chunk is rebuilt from its seed, with the differences laid back on, so
it comes back exactly as it was left.

**The NavMesh.** One NavMesh is built over the window of built chunks, off the main thread
(`UpdateNavMeshDataAsync`). It's rebuilt once the chunks have finished coming and going.

- **Instead of** a NavMesh per chunk stitched with links, which is more work for the same paths
  across a window this size.
- **Measured.** Paths of 40 to 64 m across chunk borders all completed.

**Crossing a border without stalling.** The first walk-through stuttered for 9 or 10 frames of
40 to 240 ms. Five causes, five fixes:

| cause | fix |
|---|---|
| taking a chunk down went over the whole stock once per bay: about 200 ms | a chunk's bays leave in one pass, each gap filled by the last slot, so only the slots involved are touched |
| up to five chunks came down in one frame | take-downs are queued, one a frame, after any builds |
| every chunk made its floor, ceiling and 25 lights again | shells are pooled |
| the NavMesh collected its colliders (25–45 ms) after every chunk and every 10 m walked | once a crossing, when the chunks have settled |
| the drawer showed or put away a chunk's 3,000–10,000 items at once | 3 ms' worth a frame; they're chunks away, so nobody sees them fill in |

**Now.** After the first crossing, a crossing costs 0 to 4 frames of 35 to 55 ms. That's in the
editor, on the 8 GB Mac while it was swapping.

**Trade-off.** Filling gaps from the end changes the moved slots' `Index`. Replays use `Index`,
but the hand-built store never removes slots, so its replays are unaffected.

**At full size.** 25 chunks hold 96,408 slots, six times the store's, all drawn, with 626 lights.
Rendering costs 9.2 ms at 1080p.

### 5.5 Finite per shift, endless across shifts

**The conflict.** Aiko's herding works on an aisle graph with articulation points and min-cuts.
That needs a bounded graph.

**The resolution, kept from the original plan.** The store is finite per shift and endless
across shifts: each shift would take a bounded window from the seed. That keeps Aiko's graph
analysis valid and gives the evaluation its variation.

**Not decided yet.** The maze runs in its own scene. Whether it replaces the sales floor or opens
out of it is a design call. Still to build:

- shoppers, Aiko and tasks in it;
- aisle signs per chunk;
- a floating origin, for when the player is kilometres out.

## 6. Aiko and the evaluation

### 6.1 Aiko knows only what she perceives (#10)

**Decided.** Nothing in her body, belief or decisions reads the player's position. She works
from what she perceives:

- graded sight;
- a noise bus that every player action feeds;
- traces, and customers' testimony;
- the building's sensors;
- negative evidence ("I looked there and you weren't").

Her guess is a Bayes filter over the store map's cells. **A test enforces that she doesn't read
the player.**

**Why.** The game is about being sensed, not seen through walls. It also makes the evaluation
honest: what an agent beats is a fair opponent.

### 6.2 Fairness is in the rules, with tests

- Every tactic has a tell at least 0.8 s before it.
- Every pace is capped at 94% of the player's real sprint, so sprinting always gets away (#12).
- A written warning always comes with a release window.

The first ablation runs found violations: a tell after its effect, and a re-catch straight after
a lecture. They were fixed, and the rules are tested.

### 6.3 An evaluation harness built on the real game (#10)

- **Verbs.** An agent acts through 17 verbs run through the real player body, not a model of
  it.
- **Speed.** Fixed-step headless runs play a 150 s shift in 5–15 s.
- **Access.** A local TCP server with a Python client.
- **Comparisons.** Rungs A–F of an ablation ladder, paired by seed.
- **Known limit.** Exact replay holds for the first shift after launch. Later shifts in one
  process drift a little, so runs compare paired seeds and average.

## 7. Recording and replays

### 7.1 Snapshots, not re-simulation (#15)

**Decided.** A replay records what happened, not the inputs to replay it.

**Why.** Re-simulating needs a perfectly deterministic game: physics, navigation, Aiko's
planner. Snapshots only need the recorder to listen.

**The format** (`.krec`):

- one gzip stream;
- positions as millimetre deltas in zigzag varints;
- rotations as the three smallest quaternion components at 16 bits;
- everything written only when it changes.

| | |
|---|---|
| a 6-minute shift | 380 KB (about 0.6 MB per 10 minutes, against a 20 MB budget) |
| poses read back | within 0.72 mm |

### 7.2 A replay runs the real store with the game switched off (#16)

**Decided.** The store loads as usual, then every game script, agent and the physics step are
switched off, and the recording drives the store's own objects and puppets. The puppets are
built the way the game builds each thing, then stripped of scripts.

**Why.** A replay looks exactly like the game, with no second copy of the art to maintain.

### 7.3 Clip markers only observe (#14)

The markers that find moments worth a clip listen to the shift and change nothing. Moments are
capped at 45 s. A blackout once chained a whole shift into one 5-minute "moment".

## 8. Saves, names and sound

### 8.1 Aiko's ledger is the save (#22)

Her memory of you was already written after every shift, so the main menu uses it as the
career's save. A shift left halfway isn't saved.

### 8.2 One place for the names (#13)

**Decided.** Player-facing text reads the game's and Aiko's names from one class,
`GameNames`.

**The rename's migration.** It copies old save data, never moves it, so the old data stays as a
backup.

### 8.3 The store radio runs on one clock (#5)

Every ceiling speaker plays the same clip against a single shared DSP clock, so they stay in
phase instead of echoing. Far speakers are stopped, not virtualised: a virtualised voice comes
back at the wrong point in the song.

### 8.4 Sounds made in code

Aiko's sounds and the building's are synthesised in code, normalised to one peak, with a linear
fall-off over tens of metres (#11). Unity's default fall-off made them inaudible a metre or two
away.

## 9. The pipelines: marketing and playtests

### 9.1 launchd, not a resident server (#19, #21)

**Decided.** macOS runs the pipeline's jobs on schedule. n8n is kept for looking around.

**Why.**

- A calendar time the Mac slept through runs once when it wakes.
- Nothing stays in memory between runs, which matters on 8 GB.

### 9.2 Limits built in (#16, #18)

- **Spending.** Every Claude call is priced and checked against a $15-a-month cap before it's
  made.
- **One heavy job at a time.** Unity renders and video encodes take a shared lock.
- **Dry runs.** Every step has one.

### 9.3 Playtest uploads that can't leak (#25, #26)

- **Where.** A Cloudflare Worker in front of a private R2 bucket.
- **Keys.** The upload key in testers' builds can only add. The key that lists and deletes is
  only on the Mac.
- **Recording.** The whole session is recorded from launch. A crashed session is packed and
  sent on the next launch.
- **Bug notes.** A note reaches GitHub only after a tap in Telegram, as a neutral issue that
  can't name the tester.

## 10. Known costs and open questions

- **The NavMesh rebuild** still costs about 20 ms on the main thread, once per chunk border
  crossed. That's collecting the colliders and their meshes. Caching each chunk's sources when
  it's built would move that cost into the build frames.
- **The GPU Resident Drawer grows its buffers** the first time a lot of objects arrive: 130 to
  210 ms, once.
- **The maze and the store** don't meet yet (§5.5).
- **Values saved in local prefabs** can disagree with the code (§1.1). Where a value matters,
  the code should own it.
- **Memory.** The development Mac has 8 GB. The editor in Play with the maze reached about
  6 GB, which pushes the rest of the machine into swap. Big Play-mode tests are best run with
  little else open.
